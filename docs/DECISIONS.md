# 프로덕트 결정 기록

Soul을 만들면서 내린 결정과 그 이유. 작업 전에 읽고, **이미 폐기한 안을 다시 제안하지 않는다.**

디자인·카피·접근성 규칙은 `CLAUDE.md`, 화면 시안은 `design/screens/`에 있다. 이 문서는 "왜 이렇게 만들었는가"를 담는다.

---

## 1. 서비스

### 한 줄
첫 고객 인터뷰 전에 리허설하고, 다녀온 뒤 다시 묻는 도구.

### 이름
**Soul** (2026-10-03 변경, 이전 이름 TargetTable).

> 마크(가운데 원 + 둘러앉은 점 다섯 개)는 그대로 두었다. 다만 원래 설명이던
> "과녁(Target)과 원탁(Table)은 위에서 보면 같은 모양이다"라는 말놀이는 이름이
> 바뀌면서 성립하지 않는다. **마크를 유지할지 다시 그릴지 정해야 한다.**
> 지금은 "한 자리에 둘러앉은 사람들, 위쪽 한 점은 의견이 모이는 순간"으로 읽는다.

### 흐름
```
아이디어 입력 → 타깃 추천(5명) → 3명 선택·수정·직접 생성
→ 한눈에 비교 → 단체 대화 + 1:1 → 리포트
```

### 포지셔닝 (가장 중요)
- 인터뷰를 **대체하지 않는다.** "인터뷰 전후에 쓰는 도구"다.
- AI가 검증을 끝내준다는 인상을 주지 않는다.
- 리포트의 끝은 확정된 결론이 아니라 **"다음에 물어볼 질문"**이다.

이건 취향이 아니라 검증된 결정이다. 사용자 인터뷰에서 "인터뷰를 대신한다"는 설명에 가장 강하게 반발이 나왔고, "전후에 쓰는 도구"로 바꾸자 같은 사람이 입장을 바꿨다.

### 고객
- **1차**: 첫 고객 인터뷰를 아직 못 해본 20대 예비창업자
- **2차(수익)**: 창업지원기관·대학 창업지원단 — B2B 라이선스 우선, 이후 개인으로 확장

### 수익 모델
- 기관 라이선스(B2B) 먼저 → 개인은 첫 검증 무료 + 월 구독
- **건당 과금은 폐기.** 검증은 한 번으로 끝나지 않고 계속 묻게 된다는 판단.

## 2. 이 결정의 근거 (실제 인터뷰)

지원서 작성 전 **예비창업자 5명, 액셀러레이터 2명** 인터뷰 완료.

**예비창업자(20대) 5명**
- 검증 필요성은 알지만 인터뷰는 비용·시간 부담으로 못 하고, 지인이나 AI에게 물어본다
- 인터뷰 전후로 가볍게 물어볼 수 있다는 점, 페르소나끼리 대화해 다양한 의견이 나온다는 점을 좋아함
- 다만 **"진짜 인터뷰만큼의 무게감은 아니다"** ← 이 약점을 숨기지 말고 제품에서 먼저 인정한다

**액셀러레이터 2명**
- 예비창업자의 페인포인트는 타깃·페르소나 이해도 부족
- 예비창업자와 초기창업자를 구분해야 함
- 초기에는 기관과 협업해 데이터를 축적하고, 이후 개인(B2C)으로 확장

## 3. 화면별 확정 사항

### 01 아이디어 입력
- 모두의 창업 지원서 문항 구조를 따르되 **섹션 3개(기본/아이디어/실현)**로 묶는다
- **필수는 4개만**: 한 줄 소개, 사업 분야, 어떤 아이디어인가, 문제와 차별점
- 나머지(배경, 수익 모델, 사업화 계획, 본인 역량)는 선택. 비워도 진행된다
- 파일 업로드 있음, 자동 저장

> 모두의 창업 양식을 따라가는 이유: 나중에 "검증 결과 → 지원서 초안 export"를 붙일 수 있고, 이게 기관 B2B 영업 포인트가 된다.

### 02 타깃 추천·선택
**생성 순서: 상황을 먼저 만들고, 그다음에 사람을 만든다.** (JTBD 관점)

추천 5명을 만들 때 내부적으로 확인하는 축:
- 문제를 얼마나 급하게 느끼는지
- 지금 쓰는 대안에 만족하는지
- 직접 돈을 내는 사람인지

**중요 — 이 분류를 화면에 노출하지 않는다.** "핵심 타깃", "회의적 타깃" 같은 배지는 폐기했다. 대신 "고른 이유"를 평범한 한 문장으로 쓴다. AI가 만든 분류 체계처럼 보이면 사용자가 그 틀에 갇힌다.

**단, 내부 규칙 하나는 유지**: 추천 5명 중 **이 아이디어에 시큰둥한 사람이 최소 1명**. 이게 없으면 LLM 특성상 전원이 "좋은데요?"라고 답한다. `Persona.skeptical` 플래그가 이것이다.

카드 구성:
1. 이름 + 나이·성별·직업
2. **상황 문장 2~3줄** ← 이 카드의 본문
3. 관심사 — 라벨(mono) 왼쪽 + 키워드 칩 오른쪽
4. 걱정 — 같은 형태, 충돌색
5. 그 사람 한마디 (인용)
6. 물어볼 것 / 고른 이유

> **값 3개(인터뷰 경험 / 급한 정도 / 쓸 수 있는 돈)는 폐기했다.** 카드끼리 비교는 되지만 세 칸으로 사람을 설명하려니 수치표처럼 읽혔고, 정작 "이 사람이 어떤 상황인지"가 안 보였다. 비교는 03 화면(표)이 맡고, 02는 **한 명을 제대로 이해시키는 역할**로 분리했다.
>
> **걱정은 비우지 않는다.** 비면 그 페르소나가 반대할 근거가 없어 대화에서 무조건 호의적으로 답한다. 기존 "막히는 지점"이 하던 역할을 그대로 이어받는다.

### 02-1 타깃 직접 만들기
사용자가 직접 설계할 수 있어야 한다는 게 핵심 요구였다. 네이버 NSONA의 속성 편집 방식을 참고했다.

- 왼쪽 라벨(mono) + 오른쪽 값의 **속성 편집 테이블**
- **비교할 값은 항목 이름까지 수정 가능** — 아이디어마다 중요한 축이 다르다. 이게 "직접 설계"의 핵심
- **빈 칸 채워주기** 버튼 — 이름과 상황만 쓰고 눌러도 나머지가 채워진다. 빈칸 10개를 다 채우게 하면 아무도 안 만든다
- 오른쪽에 실시간 미리보기 카드 (추천 카드와 완전히 같은 모양)
- 인터뷰 녹취·설문 파일 업로드 가능 → 그 내용을 반영해 말한다

**하단 경고 유지**: "빈 칸이 많을수록 애매하게 말해요. 막히는 지점과 쓸 수 있는 돈은 채워두세요."
직접 만든 페르소나는 창업자가 자기 편한 사람으로 만들어버릴 위험이 크다. 막히는 지점이 비면 반대할 근거가 없어서 계속 좋다고만 말하고, 그러면 검증이 아니라 자기 확인이 된다.

### 03 한눈에 보기
02와 역할이 겹치지 않게 **축을 다르게** 했다.
- 02는 한 명씩 읽고 고르는 화면(카드)
- 03은 셋을 나란히 놓고 보는 화면(표)

표의 행은 **02 카드가 실제로 가진 필드만** 쓴다: 요즘 상황 / 관심사 / 걱정 / 물어볼 것.

> 처음에는 인터뷰 경험·급한 정도·쓸 수 있는 돈을 축으로 썼다가 폐기했다. 비교는 선명했지만 **이 서비스에서만 말이 되는 축**이라, 다른 아이디어를 넣으면 채울 수 없는 칸이 생긴다. 어떤 아이디어를 넣어도 채워지는 항목만 남겼다.

상단 배너는 **관심사·걱정이 서로 다른지**를 보고 쓴다. 제목 한 줄 + 설명 한 줄.

> 구현 주의: 값이 실제로 다를 때만 "갈릴 지점"이 뜨고, 셋이 비슷하면 반대로 **"세 분이 비슷해서 의견이 잘 안 갈릴 수 있어요"**가 같은 자리에 떠야 한다.

이 화면이 하는 일은 대화 전에 "이 조합이면 쓸 만한 대화가 나오겠다"를 사용자가 판단하게 해주는 것이다.

### 04 대화 — 오버레이 방식(B안)으로 확정
- **단체 대화(1:3)가 메인 화면**을 차지한다 (중앙 880px)
- **1:1은 상단 참가자 칩을 눌러 오른쪽 460px 패널**로 연다. 뒤 단체방은 딤 처리
- 1:1 패널 상단에 **"단체 대화에서 걸려한 부분" + 그 발언 인용** — 왜 이 사람과 따로 이야기하는지가 맥락으로 붙는다
- 인원은 **1:1과 1:3 두 개로 고정**
- 라운드 구조: 첫 반응 → 상호 토론 → 자유 질문. 라운드 사이에 `[이어서 더 듣기]`
- 사용자 개입 가능, `@이름`으로 지목
- 입력창 위에 **질문 추천 칩** — 과거 행동을 묻는 쪽으로 뽑는다. "이거 쓰실 건가요?" 같은 가정형은 누구나 "네"라고 답해서 검증이 안 된다

**3명으로 고정한 이유**: 2명이면 핑퐁일 뿐 집단 역학이 없고, 3명이면 2 대 1 구도가 생겨 다수·소수 의견이 보인다. 4명 이상은 순차 발화라 레이턴시와 토큰이 늘고 읽기도 벅차다.

**B안을 고른 이유**: A안(사이드바에 방 4개)은 카톡처럼 보여서 "AI랑 채팅하는 앱"으로 읽힌다. B안은 단체 대화가 화면을 차지해 차별점이 구조로 드러나고, 1:1이 단체 대화의 특정 발언에서 파생되는 흐름이 UI에 박힌다.

**구현 결정**
- 1:1 패널이 열려 있는 동안 **단체 대화는 멈춘다.** B안에는 안 읽은 표시를 붙일 자리가 없어서, 뒤에서 계속 돌면 사용자가 놓친 걸 모른다
- MVP에서 **1:1 컨텍스트는 단체방과 분리**한다. 리포트에서만 합쳐 분석한다. (공유하는 쪽이 더 자연스럽지만 컨텍스트가 길어지고 일관성 관리가 어려워진다)

### 05 리포트 — 쟁점 단위
```
헤더 (아이디어 한 줄 · 날짜 · 참여자 · 라운드)
한 줄 결론 + 요약 문단
숫자 4개 (대화량 / 갈린 쟁점 / 입장 바뀜 / 새 이야기)
쟁점 블록 × N
  쟁점 제목 + 결과 뱃지 (갈림 / 다 동의 / 결론 안 남)
  3명 × [입장 칩 + 그렇게 말한 이유]
  읽는 법 — 왜 이렇게 갈렸는지 해석
생각이 바뀐 순간 / 예상 못 했던 이야기 / 이번 대화로는 알 수 없는 것
하단 — 이 리포트의 한계
```

**쟁점 단위인 이유**: 어떤 아이디어를 넣어도 같은 뼈대가 나온다. 커머스든 SaaS든 오프라인이든 대화하면 쟁점이 생기고, 입장이 갈리거나 모이고, 결론이 안 나는 게 남는다. "합의점 / 갈등점"처럼 결과만 나열하면 매번 모양이 달라져 템플릿이 안 잡힌다.

**"이번 대화로는 알 수 없는 것"을 반드시 남긴다.** 비우지 않는다. AI 리포트가 전부 답한 척하면 "무게감이 부족하다"는 의심이 맞다고 증명하는 꼴이다. 못 알아낸 걸 먼저 말하는 리포트가 나머지를 믿게 만든다.

**입장 칩 4단계**: 찬성(그린 틴트) / 조건부(주황 틴트) / 반대(짙은 솔리드 + 흰 글씨) / 보류(회색). 색상뿐 아니라 명도까지 갈랐다.

**"생각이 바뀐 순간"은 이유를 밝히고 바뀐 경우만 집계한다.** 이유 없이 바뀐 건 LLM 동조(sycophancy)일 수 있으므로 품질 문제로 로깅하고 파인튜닝 데이터 후보로 쓴다.

## 4. 언어 원칙

AI가 만든 조어를 쓰지 않는다. 사람이 실제로 쓰는 말로.

| 쓰지 않는 말 | 쓰는 말 |
|---|---|
| 가장 강한 신호 | 세 명 모두 공감한 부분 |
| 가장 큰 리스크 | 가장 많이 나온 걱정 |
| 반응 온도 (긍정/조건부/부정) | 써볼 것 같아요 / 이런 조건이면 / 안 쓸 것 같아요 |
| 갈등점 | 의견이 갈린 부분 |
| 입장 변화 → 셀링 포인트 후보 | 생각이 바뀐 순간 |
| 새로 나온 쟁점 | 예상 못 했던 이야기 |
| 가설 검증 보드 | 확인하고 싶었던 것 → 대화에서 나온 답 |

원칙 3개:
1. 컨설팅 보고서 말투 금지
2. 요약보다 인용 — 페르소나가 실제로 한 말을 보여주고 해석은 짧게
3. 없는 개념 만들지 않기

페르소나 카드 필드명(상황, 제약, 현재 대안)은 개발용 이름이고, 화면에는 **그 사람 목소리로** 보여준다: "요즘 이런 상황이에요", "이건 좀 부담돼요", "지금은 이렇게 해결해요".

## 5. 폐기한 안 — 다시 제안하지 않는다

| 폐기한 것 | 이유 |
|---|---|
| 대화 화면 사이드바 방 목록 (A안) | 카톡처럼 보여 "AI 채팅 앱"으로 읽힘. B안 오버레이로 확정 |
| 타깃 분류 배지 노출 (핵심/회의적/결정자) | AI 분류 체계처럼 보여 사용자가 틀에 갇힘. 내부 기준으로만 사용 |
| 5슬롯 고정 생성 | B2C인데 "결정·지불자"를 억지로 만들게 됨. 아이디어에서 자연스럽게 생성하고 뒤에서 체크만 |
| 리포트 "한 명씩 보기" 섹션 | 다중대화 인사이트에 집중. 개인 반응은 쟁점 블록 안에 녹임 |
| 건당 과금 | 검증은 한 번으로 안 끝나고 계속 묻게 됨. 구독제로 |
| 지원서 Q2를 네이버·은둔청년 사례로 쓰기 | 해커톤·아이디어톤 참여 경험 중심으로 변경 |
| 자유 입력칸 방식 아이디어 입력 | 모두의 창업 문항 구조로 확정 |
| `product_proficiency` 필드 | 이미 존재하는 제품 기준이라 우리에게 안 맞음. "지금 쓰는 것"으로 대체 |

## 7. LLM 로드맵

**파인튜닝은 당장 하지 않는다.**
```
1. Prompt only
2. Orchestrator 개발
3. 평가셋 제작
4. 문제 유형 확인
5. LoRA/SFT
```

### 무엇을 학습시키나
페르소나 자체가 아니라 **페르소나를 연기하는 방식**이다. "24세 예비창업자 박민수"를 가중치에 넣는 게 아니다. 페르소나는 매번 바뀌므로 프롬프트/컨텍스트로 주입한다.

학습 대상 8가지:
1. **Persona adherence** — 카드 밖 정보를 마음대로 만들지 않기
2. **Behavioral consistency** — 앞에서 "가격에 민감"이라 해놓고 뒤에서 "가격은 상관없다"고 하지 않기
3. **Non-sycophancy** — 다른 페르소나가 말한다고 무조건 동의하지 않기
4. **Conditional agreement** — "그 점은 맞지만 제 상황에서는…"
5. **Grounded disagreement** — 성격이 아니라 자신의 상황 때문에 반대하기
6. **Natural multiparty dialogue** — 매번 장문의 보고서처럼 답하지 않기
7. **Dialogue-act behavior** — 질문받으면 답하고, 반박받으면 그 주장에 대응하기
8. **Epistemic restraint** — 카드에 없는 경험을 "제가 실제로 써봤는데요"라고 지어내지 않기

### 오케스트레이터 구현 주의
- **쟁점은 리포트 생성 때 한 번에 뽑지 말고, 대화 중에 미리 태깅해 둔다.** 대화가 끝난 뒤 "무엇이 쟁점이었나"를 추출하는 건 모델이 자주 틀린다
- 발화는 순차라 반드시 토큰 단위 스트리밍
- LLM 호출은 서버에서만. 키가 클라이언트로 나가면 안 된다

### 평가 지표 (제안 — 확립된 표준 아님)
- **1:1 대비 신규 쟁점 수** — 같은 페르소나에게 1:1로만 물었을 때 대비, 단체 대화에서만 새로 나온 논점 개수. 가장 설득력 있는 베이스라인 비교
- **입장 다양성** — 서로 다른 스탠스의 개수
- **근거 없는 동조율** — 이유 없이 입장을 바꾼 비율
- **페르소나 일관성** — 카드 속성과 모순되는 발화 비율

### ⚠️ 모델 선택 — 확인 필요
아래는 **미확인 정보**다. 결정 전에 직접 확인할 것.
- Qwen 계열에서 이름에 **Plus/Max가 붙은 건 역대로 API 전용**이었다. 가중치 공개 여부를 확인해야 한다. 비공개면 LoRA 불가
- Kimi K2는 총 1T 파라미터 MoE(활성 32B)였다. K3가 비슷한 규모면 로컬 파인튜닝은 현실적으로 불가능
- 14B 모델은 bf16 기준 가중치만 약 28GB. 4bit 양자화 시 대략 8~9GB
- 단체 대화는 순차 발화라 페르소나 3명이면 레이턴시가 그만큼 누적된다
- 서비스로 24시간 돌리려면 개인 PC가 아니라 서버가 필요
- 다만 **"아이디어가 외부 API로 안 나간다"**는 건 창업자에게 먹히는 셀링 포인트가 될 수 있다 (실제로 사내 기획자 페르소나가 이 우려를 말했다)
- **MVP는 API로 빠르게 가고, 로컬화는 이후에** 하는 게 현실적

### ⚠️ 학습 데이터 주의
실제 단톡방 대화를 참여자 동의 없이 수집하면 개인정보 이슈가 생긴다. 동의서를 받거나, 합성 데이터에 사람이 라벨링하는 방식이 안전하다.

## 8. 알려진 리스크

- **같은 모델의 3명은 의견이 수렴하기 쉽다.** 베이스 모델이 같으니 합의가 진짜 합의가 아니라 모델 편향일 수 있다. 대응: 회의적 슬롯 고정 + 리포트에 "만장일치 = 오히려 의심" 관점
- **페르소나가 경험을 지어낼 위험.** "제가 써봤는데요" 같은 발화가 리포트 인용에 들어가면 신뢰가 깨진다. 카드에 없는 경험은 인용 대상에서 제외
- **리포트를 너무 얇게 만들면** "그냥 ChatGPT한테 물어본 거랑 뭐가 달라?"가 된다. 쟁점별 "읽는 법" 해석이 차별점을 만드는 자리다
